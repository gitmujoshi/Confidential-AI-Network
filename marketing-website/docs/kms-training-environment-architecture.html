    1. Executive Summary

    1.1 Overview

    This document explains how KMS (Key Management Service) actually works in confidential computing environments during AI model training. The system provides end-to-end encryption, secure key management, and automated training execution in encrypted, isolated environments.

    1.2 Key Features

  • KMS Integration: Centralized key management for DID:web, data encryption, and model encryption
  • Data Encryption: Encrypted storage and transmission of datasets and models
  • Automatic Provisioning: Training environments provisioned based on contract specifications
  • Automated Training: Training execution triggered when all parties sign contracts
  • Confidential Computing: Secure processing in encrypted VMs/containers
  • Contract-Driven: Training containers interpret contracts and execute accordingly

    3. How KMS Works in Confidential Computing

    3.1 The Complete Training Flow

    This is how KMS actually works during training in confidential computing environments:

    #### Phase 1: Contract Signing & Key Distribution
  • Contract Creation: TDC creates contract specifying training requirements
  • Key Generation: KMS generates unique encryption keys for this training session
  • Key Distribution: Keys are distributed to all parties (TDP, TDC, CCRP) via secure channels
  • Contract Signing: All parties sign the contract using their DID:web keys
    • #### Phase 2: Environment Provisioning
  • CCRP Provisioning: CCRP provisions encrypted Azure Container Instances
  • Key Injection: Training container receives session keys via secure key injection
  • Environment Isolation: Container runs in encrypted, isolated environment
  • Access Control: Only authorized training processes can access the keys
    • #### Phase 3: Training Execution
  • Data Decryption: Training container decrypts datasets using KMS-provided keys
  • Model Loading: AI model is loaded and decrypted in memory
  • Secure Training: Training runs in encrypted memory space
  • Result Encryption: Training results are encrypted before storage/transmission

    • 3.2 KMS Key Management During Training

    sequenceDiagram participant TDC as Training Data Consumer participant KMS as Key Management Service participant CCRP as CCRP Provider participant Container as Training Container participant Azure as Azure Cloud TDC->>KMS: Request training session keys KMS->>KMS: Generate session-specific keys KMS->>TDC: Return encrypted session keys TDC->>CCRP: Provision training environment CCRP->>Azure: Create encrypted container CCRP->>Container: Inject session keys securely Container->>KMS: Request data decryption keys KMS->>Container: Provide decryption keys Container->>Container: Decrypt and train Container->>KMS: Encrypt training results Container->>TDC: Return encrypted results

    3.3 Key Types and Their Roles

    #### Session Keys (Training-Specific)
  • Purpose: Unique keys for each training session
  • Lifecycle: Generated when contract is signed, destroyed after training
  • Usage: Encrypt/decrypt data during training execution
  • Storage: Stored in Azure Key Vault, injected into training containers
    • #### Data Encryption Keys
  • Purpose: Encrypt datasets uploaded by TDPs
  • Lifecycle: Long-lived, rotated periodically
  • Usage: Decrypt datasets when training begins
  • Storage: Stored in KMS, never exposed to training containers
    • #### Model Encryption Keys
  • Purpose: Encrypt AI models provided by TDCs
  • Lifecycle: Generated per model, stored securely
  • Usage: Decrypt models when loading into training environment
  • Storage: Stored in KMS, accessed via secure API calls
    • #### DID:WEB Keys
  • Purpose: Identity verification and contract signing
  • Lifecycle: Long-lived, stored in user wallets
  • Usage: Sign contracts, verify identity
  • Storage: Stored in user's DID wallet, never in KMS

    4. TDC and TDP Encryption Key Management

    4.1 TDP (Training Data Provider) - Dataset Encryption

    #### Key Generation & Management:
  • TDP generates their own encryption keys for datasets before upload
  • Keys are NOT stored in the central KMS - they remain under TDP control
  • Datasets are encrypted locally by TDP before transmission
  • Only encrypted datasets are uploaded to the system
    • #### Security Model:
    graph LR subgraph "TDP Environment" TDP[Training Data Provider] LocalKeys[Local Encryption Keys] RawData[Raw Datasets] EncryptedData[Encrypted Datasets] end subgraph "Contract Management System" KMS[KMS Service] SessionKeys[Training Session Keys] TrainingContainer[Training Container] end TDP -->|Generates| LocalKeys LocalKeys -->|Encrypts| RawData RawData -->|Becomes| EncryptedData EncryptedData -->|Uploads| ContractSystem KMS -->|Provides| SessionKeys SessionKeys -->|Decrypts| EncryptedData
    #### TDP Workflow:
  • Local Encryption: TDP encrypts datasets with their own keys
  • Secure Upload: Only encrypted data is transmitted
  • Key Sharing: TDP shares decryption keys via secure channels when training begins
  • Training Access: Training container receives keys to decrypt datasets
  • Key Destruction: Session keys destroyed after training completion

    • 4.2 TDC (Training Data Consumer) - Model Encryption

    #### Key Generation & Management:
  • TDC generates encryption keys for their AI models
  • Models are encrypted locally before upload
  • Keys remain under TDC control until training session
  • Only encrypted models are stored in the system
    • #### Security Model:
    graph LR subgraph "TDC Environment" TDC[Training Data Consumer] ModelKeys[Model Encryption Keys] RawModel[Raw AI Model] EncryptedModel[Encrypted Model] end subgraph "Training Environment" KMS[KMS Service] SessionKeys[Training Session Keys] TrainingContainer[Training Container] end TDC -->|Generates| ModelKeys ModelKeys -->|Encrypts| RawModel RawModel -->|Becomes| EncryptedModel EncryptedModel -->|Uploads| TrainingSystem KMS -->|Provides| SessionKeys SessionKeys -->|Decrypts| EncryptedModel
    #### TDC Workflow:
  • Local Encryption: TDC encrypts AI models with their own keys
  • Secure Storage: Only encrypted models are stored
  • Key Provisioning: Keys provided to training environment when needed
  • Training Execution: Model decrypted in secure memory during training
  • Secure Cleanup: All decrypted data erased after training

    4.4 Security Benefits of This Approach

    #### Data Privacy:
  • TDPs maintain control over their dataset encryption keys
  • TDCs maintain control over their model encryption keys
  • No single point of failure for key management
  • Data remains encrypted until explicitly needed for training
    • #### Access Control:
  • Keys only shared when training contracts are signed
  • Temporary access during training sessions only
  • Automatic key rotation for each training session
  • Audit trail of all key access and usage
    • #### Compliance:
  • GDPR compliance through data encryption at rest
  • Data residency maintained by TDP/TDC control
  • Audit logging of all encryption/decryption operations
  • Secure key transmission via encrypted channels

    Summary

    KMS in confidential computing works by:

  • Generating unique session keys for each training session

  • Securely distributing keys to all authorized parties
  • Provisioning encrypted training environments in Azure
  • Injecting keys securely into training containers
  • Running training in encrypted memory with continuous monitoring
  • Destroying session keys after training completion

    • Key Management Summary:

    #### TDP Responsibilities:
  • ✅ Generate encryption keys for datasets
  • ✅ Encrypt datasets locally before upload
  • ✅ Provide decryption keys when training begins
  • ✅ Maintain key security throughout the process
    • #### TDC Responsibilities:
  • ✅ Generate encryption keys for AI models
  • ✅ Encrypt models locally before upload
  • ✅ Provide decryption keys when training begins
  • ✅ Maintain key security throughout the process
    • #### KMS Responsibilities:
  • ✅ Generate session keys for training sessions
  • ✅ Coordinate key distribution to training containers
  • ✅ Manage key lifecycle during training
  • ✅ Ensure secure key destruction after training
    • #### System Benefits:
  • 🔒 End-to-end encryption from data source to training completion
  • 🎯 Granular access control based on training contracts
  • 📊 Audit trail of all encryption/decryption operations
  • 🚀 Scalable architecture supporting multiple TDPs and TDCs

The key insight is that KMS doesn't just store keys - it actively manages the entire lifecycle of encryption keys during training, ensuring that sensitive data and models are never exposed in plain text, even during processing. TDPs and TDCs maintain full control over their encryption keys while enabling secure, contract-driven training in confidential computing environments.

This architecture provides enterprise-grade security for AI training while maintaining the flexibility and automation needed for production use.
